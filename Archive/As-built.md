### Gotchas (2026-08-06 additions, 8th session — 스탯 시스템 기획서 정합화)

- **새 게임 시스템(스탯/전투 공식 등)을 설계하기 전에 `Docs/랜덤 플래닛 전체 기획서.md`에 이미 구체적인 수치·공식이 있는지 먼저 확인할 것.** 7차 세션에서 STR/DEX/INT/LUK의 전투 효과를 AI가 처음부터 설계했는데(INT→최대체력 등), 기획서 §2-2/§8-1에 이미 정확한 주/부 효과와 포인트당 계수가 명시돼 있었다는 걸 8차에서야 발견 — INT는 원래 스킬데미지+최대MP 전용이지 체력과 무관했고, DEX의 주/부 효과가 뒤바뀌어 있었다. **교훈**: `랜덤 플래닛 전체 기획서.md`는 `랜덤 플래닛 인게임.md`(As-built가 매 세션 갱신하는 실제 구현 GDD)와 별도 파일이라 존재를 잊기 쉽지만, 스탯/전투/특성처럼 원 기획에 수치까지 박혀있는 시스템을 만들 땐 반드시 먼저 grep해서 관련 절이 있는지 확인해야 한다.
- **기획서의 스탯 공식을 문자 그대로 구현하면 스탯 간 순수 DPS가 2.8~3배까지 벌어질 수 있다** — STR(물리공격력, 캡 없는 선형 +2/pt)과 DEX/LUK(공격속도·크리확률, 둘 다 %기반+캡 있음)는 근본적으로 다른 스케일링 곡선이라, 캐릭터 생성 스탯 범위(1~17 정도)에서 이미 STR 몰빵이 압도적으로 유리함을 `Lobby` 맵 실측(TrainingDummy, 넉백 없는 순수 DPS 비교)으로 확인. 유저 결정으로 STR 계수를 +2→+1.5/pt로 완화(70 dps, 원안 73.3 dps 대비 소폭 감소, DEX 24/LUK 26.3과의 격차 축소) — 완전한 수치 동일화는 하지 않음(STR이 확실한 주력 딜 스탯이라는 정체성은 유지). **교훈**: 캡 없는 선형 스탯 vs 캡 있는 %기반 스탯을 같은 포인트 풀로 분배하는 설계는 항상 이런 쏠림이 생기므로, 실제 계수를 코드로 옮기기 전에 대표 스탯값으로 최종 결과값을 미리 계산/실측해볼 것.
- **`RigidbodyComponent:AddForce`는 순간 임펄스가 아니라 지속되는 힘처럼 작동한다** — STR 보조 효과로 "몬스터에게 넉백을 가함"을 처음 구현했을 때, 몬스터가 한 방에 7유닛 이상 날아갔고 `RigidbodyComponent.Mass`를 10000까지 올려도 크게 줄지 않았다(문서상 "Mass가 클수록 반응성이 낮아진다"고 되어 있으나 실측상 눈에 띄게 감쇠하지 않음 — Mass 스케일 감각이 문서 설명과 다를 수 있음). 결국 이 설계 자체를 기획서 기준("넉백 저항", 즉 몬스터→플레이어 방향)으로 바꾸면서 자연히 사라진 문제지만, **몬스터에게 AddForce로 넉백을 주는 향후 작업(전직 스킬 등)이 있다면 Mass 튜닝만으로 거리를 통제하려 하지 말고, 작은 원포인트 값으로 시작해 실측하며 올릴 것.**

- **`PlayerHUDController`(신규 `@Logic`)에서 `property` 미선언인 `self.timerId`에 대입하면 `"cannot set timerId, no such field"` 런타임 에러.** `msw-ui-system/references/runtime-patterns.md`의 일부 예제(`UIToast` 등)는 `property` 선언 없이 `self.timerId = _TimerService:SetTimerRepeat(...)`를 그대로 쓰지만, 실제 엔진은 `msw-scripting/SKILL.md` §5가 명시하는 대로 **반드시 `property any timerId = nil`(또는 `property integer timerId = 0`) 선언이 필요**하다 — 미선언 상태에선 컴파일은 통과하지만(LSP도 잡지 못함) 런타임에서만 실패한다. 처음엔 이 에러 때문에 HUD 갱신 타이머가 아예 안 걸려서 HP/XP 바가 "88 / 88" 같은 정적 텍스트만 남고 갱신 안 되는 상태였음 — `Docs/RandomPlanet-M1-Phase2.md` Task 3 결과 참고. **교훈**: `runtime-patterns.md`의 mlua 스니펫을 그대로 복붙할 때도 `property` 선언 목록까지 전부 포함됐는지 확인할 것 — 일부 레시피는 지면상 `_T`/타이머 프로퍼티 선언을 생략하고 있다.
- **`PlayerAttack.DoAttack()`을 `maker_execute_script`로 직접 호출해 전투를 테스트할 때, `PlayerControllerComponent.LookDirectionX`가 이동 입력 없이는 갱신되지 않아 공격이 몬스터 반대 방향으로 나갈 수 있다.** `msw-combat-system` §9-1이 이미 문서화한 케이스("Auto-attack / AI-triggered attack must set facing first")를 실제로 겪음 — 플레이어를 몬스터 옆으로 순간이동시킨 뒤 곧바로 `DoAttack()`을 호출하면 `LookDirectionX`는 마지막 실제 이동 입력 방향(이 세션에선 -1, 왼쪽)에 머물러 있어서 공격 판정 박스가 몬스터 반대편에 생성됐다. **해결**: 스크립트로 직접 공격을 트리거하기 전에 `controller.LookDirectionX = (targetX >= selfX) and 1 or -1`로 명시적으로 향해준다. 실제 키/터치 입력으로 플레이하는 정상 경로는 이동 시 자동 갱신되므로 이 문제와 무관 — 이건 순수히 "이동 없이 직접 스크립트로 공격만 트리거하는" 테스트 방법론의 함정이다.

## Phase 0 — Character Select (done)

**Interaction model** (revised 2026-07-16): 6 character-standee slots stand simultaneously on `choice_map`'s foothold. Click an empty slot → instant random-character creation + gacha-style stat reveal (unchanged). Click an **occupied** slot **once** → only selects it (glow ring moves there), no card. **Double-click** (within 0.4s) the same occupied slot → opens the card UI showing level/trait/stats + PLAY + a delete button (bottom-right corner of the card). No `.ui` overlay is used for the stage itself — only the small popup card. **Why single vs. double click was introduced**: the delete button used to be a standalone world entity (`BtnDelete`) at a fixed world position, which visually collided with whichever standee ended up physically nearby (reported as "button overlap" on slot 3) - moving delete into the card (only reachable via an explicit double click) removes it from world-space entirely, so it can never again collide with a standee.

### Full playtest pass + nametag immersion fix (2026-07-31, second session)

Ran a real end-to-end playtest — actual `maker_mouse_input`/`maker_keyboard_input` where the input layer allows it, not just `maker_execute_script` shortcuts — covering: empty-slot click→create→gacha reveal, delete-confirm dialog, PLAY→Lobby, NPC touch→squad-formation popup, Lobby standee click→character swap, up-arrow→return portal. All verified working via real input with screenshot + log evidence; 0 build errors.

- **`maker_mouse_input` world-space clicks require calibration, not visual pixel-reading from a screenshot.** A raw guess from eyeballing a screenshot's pixel position missed every time; the reliable method (same one already documented below for `maker_mouse_input`'s world↔screen mapping) is to query `_UILogic:ScreenToWorldPosition` at 2-3 known screen points (e.g. `(0,0)` and `(width,0)`) via `maker_execute_script` **immediately before** the click, solve the linear map, then convert the target's world position to a click position. The map/camera state was confirmed stable across repeated calibration queries in this session (not actually drifting) — the earlier suspicion of a moving camera was wrong; the real cause of missed clicks was always visual mis-estimation. Recalibrate fresh per map (`choice_map` and `Lobby` had different offsets, same scale) rather than reusing a stale constant.
- **`maker_logs` can lag behind a just-fired click by a few seconds** — querying immediately after a click sometimes shows no new entries even though the click landed and its handler ran (confirmed by a `maker_screenshot` taken moments later showing the correct resulting UI state, followed by the handler's log line appearing on the *next* `maker_logs` call). Don't conclude "the click missed" from an immediately-empty log diff alone — cross-check with a screenshot or a follow-up log query before treating it as a failure.
- **Lua's `a and b or c` idiom silently misreports when `b` is `false`** — a diagnostic script wrote `isvalid(x) and x.Comp.Enable or nil` intending "nil if invalid, else the real Enable value," but when `Enable` is genuinely `false` the whole expression falls through to `nil` (`true and false` → `false`, `false or nil` → `nil`), making a correctly-`false` (hidden, as intended) state look identical to "the object doesn't exist." This produced a false-alarm "missing NameTag" investigation this session before the mistake was caught — the actual game state (`LobbySlot3`/`5`/`6`'s `AvatarBody`/`NameTag` correctly `Enable=false` while hidden/empty) was correct the whole time. **Never use the `a and b or c` idiom when `b` can legitimately be `false`** — use an explicit `if/else` or ternary-safe helper instead, in test scripts as much as in shipped code.
- **Fixed (immersion polish)**: `CharacterRosterLogic.ShowLocalPlayer()` no longer re-enables `NameTagComponent` — it used to show the player's real MSW account nickname (e.g. "discusning") floating above the actively-played character, which reads as inconsistent with this game's "nameless randomly-rolled character" concept (every standee only ever shows "Lv.N", never an account name) in a solo-only game (no other player ever needs to read this nametag — GDD §2). `AvatarRendererComponent` is still re-enabled as before; only the nametag stays hidden through actual gameplay now, not just the character-select stage. Verified via screenshot before/after.

### Gotchas (2026-08-03 additions, 6th session — full QA sweep)

- **`EquipmentLogic.GetEffectiveStat(data, "int")` always returned the equipment bonus only, never the character's base INT — base-stat field name mismatch.** The roster stores base stats as `{ str, dex, intel, luk }` (`CharacterSelectStageController.CreateCharacter`), but `GetEffectiveStat`'s base lookup was `characterData[stat] or 0` with `stat` passed as the literal string `"int"` (matching the `tpl.bonusInt`/equipment-bonus branch, not the base-field name) — `characterData["int"]` is always `nil`, so effective INT silently floored to `0 + equipment bonus` regardless of the real base value. STR/DEX/LUK were unaffected since their base field names (`str`/`dex`/`luk`) happen to match their stat-key strings exactly; only INT/`intel` diverges. Found via a real screenshot-driven QA pass (equipment popup showed "STR 7 DEX 3 INT 0 LUK 4" for a character whose card had just shown INT 6) and confirmed reproducible on 3 different characters before fixing. **Fix**: in `GetEffectiveStat`, remap only the base-lookup key (`if stat == "int" then baseField = "intel" end`) — the `"int"` identifier still flows unchanged into the `tpl.bonusInt`/`inst.bonusInt` branches below, so equipment-bonus behavior is untouched. Re-verified via `log()` across 3 characters: effective INT now matches raw `intel` exactly (6/3/10), no regression on STR/DEX/LUK. **Lesson**: whenever a stat/field identifier crosses between "the character data's own field name" and "a shared bonus-lookup key," verify they're actually the same string for every stat — a mismatch that only affects one stat out of four is easy to miss in code review and won't throw an error, it just silently reads `nil → 0`.

### Architecture risk — single shared `currentIndex`

`OnDeleteTouched()` (and the world "생성" button) always act on `self._T.currentIndex`, not on "whichever slot the user thinks they picked." Selection is a **separate prior step** (`OnStandeeTouched` updates `currentIndex`) from the destructive action (delete). If a standee click is ever missed/mis-registered, `currentIndex` silently stays on the last *successful* selection, and the next delete removes that slot instead of the one the user was looking at. This was the leading theory behind an earlier user report of "only the last-created character is deletable" — since **confirmed** to have been exactly this: missed clicks caused by the `TouchReceiveComponent` narrow-hitbox bug (see Gotchas + "Resolved report" below), not a bug in the `currentIndex` model itself. Now that click detection is reliable (`ScreenTouchEvent`-based), `currentIndex` reliably tracks the last-touched slot and this risk is latent rather than active — but the design coupling (selection and delete sharing one index) is still worth keeping in mind if a future feature reintroduces missed/async selection (e.g. multi-touch, network lag on a synced index).

### Gotchas (do not redo these mistakes)

- **`TextRendererComponent.FontSize` is not in world units.** It's a separate scale — values in the 2.5–6 range read as normal text at this project's camera zoom; 0.6 is nearly invisible, 40 fills the screen. Tune visually via screenshot, don't guess from `RectSize`.
- **`SortingLayer` must match the map's actual `MapLayerComponent.MapLayerName`**, not a guessed default like `"MapLayer0"`. Check via `MapBuilder.component(mapLayerEntityName, "MOD.Core.MapLayerComponent")` before setting world text/sprite `SortingLayer`.
- **Avatar rendering needs its own child entity, not the root.** `AvatarRendererComponent`+`CostumeManagerComponent` on the same root Transform as a foothold-offset silhouette sprite renders the avatar floating in mid-air (avatar = foot-pivot, silhouette = center-pivot workaround). Put the avatar stack on a child with a local Y offset canceling the root's offset.
- **`TouchReceiveComponent` is unreliable on any entity that swaps its visible renderer between a root `SpriteRendererComponent` and a child `AvatarRendererComponent`** (exactly the standee's empty↔filled swap). Confirmed root cause: an occupied standee's actual touch hitbox is only ~±15px around the exact `TransformComponent` center — far smaller than the visible avatar sprite a human naturally clicks at torso/face height. This held regardless of setting: `AutoFitToSize=true` (baseline), `AutoFitToSize=false` + fixed `TouchArea` up to `(1.2,2.2)`, and even `TouchArea=(4,4)` all failed the same off-center-click test. **Fix applied: removed `TouchReceiveComponent` from the standee model entirely**, replaced with a global `_InputService:ConnectEvent(ScreenTouchEvent, ...)` handler on the stage controller that converts the touch point via `_UILogic:ScreenToWorldPosition()` and does a manual box-distance hit test against each standee's real world position (see Data flow). Filtered by `_InputService:IsPointerOverUI()` so UI-button clicks aren't double-handled. Verified via repeated off-center click regression tests on both empty and occupied slots. **If a future entity needs click detection and also swaps renderers (sprite↔avatar, sprite↔skeleton, etc.), assume `TouchReceiveComponent` will have the same narrow-hitbox problem and go straight to the `ScreenTouchEvent` pattern instead of re-testing `TouchArea` tuning.**
- **UI-attached components cannot call `@ExecSpace("Server")` service methods directly** in this world (`ServiceAuthorityCheck=true` in `WorldConfig.config` → `[LEA-3022] InvalidExecSpace`). Route server calls through a real map/world-entity component instead (see `RequestEnterGame` on `CharacterSelectStageController`, called from the UI card via `GetComponent`).
- **`table` is a valid cross-boundary RPC parameter type** (client→server `@ExecSpace("Server")` calls) — confirmed working for a flat table of 6 strings (`look`). Prefer this over long individual-argument lists when a script boundary is crossed.
- **World UI panels here do not block world-entity touch input by default** (`raycast: false` is the builder default for `panel()`). A standee positioned underneath an open card UI is still clickable — don't assume "the card covers it" explains an input bug.
- **`SpawnLocationComponent`-bearing entities must be named exactly `SpawnLocation`.** Maker auto-suffixes duplicates (`SpawnLocation_1`, `_2`, ...) which the engine rejects (`[LEA-3021]`) — multiple entities sharing the identical name `SpawnLocation` is the correct/expected pattern for this component, not a conflict. Fix via `MapBuilder.rename()`.
- **World start map is a Maker-project-level setting with no corresponding workspace file** (no `Global/SectorConfig.config` in this project). Cannot be set by AI file edit — user must configure it in the Maker UI. Verify via `maker_get_current_map()` after `play`.
- **`SpriteRendererComponent.TiledSize` on `DrawMode=Sliced`/`Tiled` is NOT the world-unit draw-area size it appears to be from the `.d.mlua` description ("Sets the size of an area where the sprite will be drawn").** For this project's default placeholder sprite (RUID `1705e3c5b2c146ac9a699f96fb067408`, 24×24 native px, 100 PPU → 0.24 world-unit native size), empirically (confirmed via screenshot pixel measurement across three test values) the actual rendered size is `TiledSize × 0.24`, i.e. `TiledSize` behaves as a **multiple of the sprite's own native world-unit size**, not an absolute target size. A `TiledSize` of `(1.8, 0.6)` intended to mean "1.8×0.6 world units" instead rendered at ~0.43×0.14 — invisible/tiny until moved off the tile-map layer where it became noticeable as a small patch instead of a full chip. **Fix**: compute `TiledSize = desired_world_size / 0.24` (e.g. for a 1.72×0.5-unit chip, use `TiledSize = (7.17, 2.08)`). This affected `CharacterStandee.model`'s `CreateBg`/`CreateBorder`/root silhouette and `WorldButton.model`'s root fill/`Border` — all originally authored with the wrong (too-small) assumption; corrected 2026-07-16.
  **✅ Generalized and confirmed 2026-08-03 (5th session)**: the "specific to this one placeholder RUID?" question was open until this session. Placed two inline `MapBuilder.sprite()` test entities in `Lobby` side by side, both `DrawMode=1`(Sliced) `TiledSize=(2,2)`: the known placeholder (24×24px native) rendered a clean 40×40px box (confirmed against a self-measured screenshot scale — matches the established `×0.24` prediction), while a **different** RUID (`f92c6c9b127d4c3d8fedc54609a9464c`, a 176×124px "object"-category sign sprite found via `msw-search`) with the **identical** `TiledSize=(2,2)` rendered dramatically larger (~350+ px wide vs. the placeholder's 40px — an 8×+ difference, decisively distinguishing the two competing hypotheses). This confirms the formula generalizes: **`rendered_size = TiledSize × (native_width_px/100, native_height_px/100)` per axis, for any sprite** — the `×0.24` constant was never special to the engine, it was simply `24px/100` applying identically to both axes of that one square placeholder. **When authoring `TiledSize` for a new (non-placeholder) sprite, first look up its native `payload.width`/`payload.height` via `msw-search`'s `getResource`, then divide the desired world-unit size by `(width/100, height/100)` per axis** — do not assume `0.24` applies to a different sprite. Secondary finding from the same test: one `sprite`-typed RUID from an `"etc"`-category search result (a `52×24px` UI-style button texture reading "취소") rendered **nothing at all** in world `SpriteRendererComponent` under both `Sliced` and `Tiled` modes (silent failure, no build/runtime error) despite identical component wiring to the working reference — not every `type:"sprite"` search result is safe to use in a world `SpriteRendererComponent`; verify visually via a real screenshot before relying on a newly-found RUID, especially ones from `category:"etc"`.
- **Both `SpriteRendererComponent` (Sliced/Tiled) and `TextRendererComponent` anchor `TransformComponent.Position` at the visual box's BOTTOM-LEFT corner and grow UP+RIGHT as `TiledSize`/`RectSize` increases — not center-anchored.** Confirmed via precise pixel-bound measurement: two sprites given the *same* `Position` but different `TiledSize` (a fill + an intended "border" 0.1 unit larger on each axis) rendered with identical left edges and identical bottom edges, with the larger one sticking out **only** on the top and right — never the left or bottom. The initial `CreateBorder`/`WorldButton.Border` implementation (2026-07-16, first pass) set the border to the *same* position as its fill assuming center-anchoring, producing an "L-shaped" border visible only on two sides. **Fix**: derive every position from the desired *visual center*, not the naive shared-origin assumption: `position = desired_center - size/2` (for both sprite `TiledSize` and text `RectSize`, per axis). Re-verify with a pixel-bound measurement (not just eyeballing a screenshot) after any resize — a small enough size mismatch can look "close enough" at a glance while still being measurably lopsided.
- **`TextRendererComponent`'s effective vertical text position does not cleanly follow the `position = center - RectSize/2` formula in practice**, even though it fixed the horizontal case reasonably well.
