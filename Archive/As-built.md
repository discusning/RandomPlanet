- **새 게임 시스템(스탯/전투 공식 등)을 설계하기 전에 `Docs/랜덤 플래닛 전체 기획서.md`에 이미 구체적인 수치·공식이 있는지 먼저 확인할 것.** 7차 세션에서 STR/DEX/INT/LUK의 전투 효과를 AI가 처음부터 설계했는데(INT→최대체력 등), 기획서 §2-2/§8-1에 이미 정확한 주/부 효과와 포인트당 계수가 명시돼 있었다는 걸 8차에서야 발견 — INT는 원래 스킬데미지+최대MP 전용이지 체력과 무관했고, DEX의 주/부 효과가 뒤바뀌어 있었다. **교훈**: `랜덤 플래닛 전체 기획서.md`는 `랜덤 플래닛 인게임.md`(As-built가 매 세션 갱신하는 실제 구현 GDD)와 별도 파일이라 존재를 잊기 쉽지만, 스탯/전투/특성처럼 원 기획에 수치까지 박혀있는 시스템을 만들 땐 반드시 먼저 grep해서 관련 절이 있는지 확인해야 한다.
- **기획서의 스탯 공식을 문자 그대로 구현하면 스탯 간 순수 DPS가 2.8~3배까지 벌어질 수 있다** — STR(물리공격력, 캡 없는 선형 +2/pt)과 DEX/LUK(공격속도·크리확률, 둘 다 %기반+캡 있음)는 근본적으로 다른 스케일링 곡선이라, 캐릭터 생성 스탯 범위(1~17 정도)에서 이미 STR 몰빵이 압도적으로 유리함을 `Lobby` 맵 실측(TrainingDummy, 넉백 없는 순수 DPS 비교)으로 확인. 유저 결정으로 STR 계수를 +2→+1.5/pt로 완화(70 dps, 원안 73.3 dps 대비 소폭 감소, DEX 24/LUK 26.3과의 격차 축소) — 완전한 수치 동일화는 하지 않음(STR이 확실한 주력 딜 스탯이라는 정체성은 유지). **교훈**: 캡 없는 선형 스탯 vs 캡 있는 %기반 스탯을 같은 포인트 풀로 분배하는 설계는 항상 이런 쏠림이 생기므로, 실제 계수를 코드로 옮기기 전에 대표 스탯값으로 최종 결과값을 미리 계산/실측해볼 것.
- **`RigidbodyComponent:AddForce`는 순간 임펄스가 아니라 지속되는 힘처럼 작동한다** — STR 보조 효과로 "몬스터에게 넉백을 가함"을 처음 구현했을 때, 몬스터가 한 방에 7유닛 이상 날아갔고 `RigidbodyComponent.Mass`를 10000까지 올려도 크게 줄지 않았다(문서상 "Mass가 클수록 반응성이 낮아진다"고 되어 있으나 실측상 눈에 띄게 감쇠하지 않음 — Mass 스케일 감각이 문서 설명과 다를 수 있음). 결국 이 설계 자체를 기획서 기준("넉백 저항", 즉 몬스터→플레이어 방향)으로 바꾸면서 자연히 사라진 문제지만, **몬스터에게 AddForce로 넉백을 주는 향후 작업(전직 스킬 등)이 있다면 Mass 튜닝만으로 거리를 통제하려 하지 말고, 작은 원포인트 값으로 시작해 실측하며 올릴 것.**

- **`PlayerHUDController`(신규 `@Logic`)에서 `property` 미선언인 `self.timerId`에 대입하면 `"cannot set timerId, no such field"` 런타임 에러.** `msw-ui-system/references/runtime-patterns.md`의 일부 예제(`UIToast` 등)는 `property` 선언 없이 `self.timerId = _TimerService:SetTimerRepeat(...)`를 그대로 쓰지만, 실제 엔진은 `msw-scripting/SKILL.md` §5가 명시하는 대로 **반드시 `property any timerId = nil`(또는 `property integer timerId = 0`) 선언이 필요**하다 — 미선언 상태에선 컴파일은 통과하지만(LSP도 잡지 못함) 런타임에서만 실패한다. 처음엔 이 에러 때문에 HUD 갱신 타이머가 아예 안 걸려서 HP/XP 바가 "88 / 88" 같은 정적 텍스트만 남고 갱신 안 되는 상태였음 — `Docs/RandomPlanet-M1-Phase2.md` Task 3 결과 참고. **교훈**: `runtime-patterns.md`의 mlua 스니펫을 그대로 복붙할 때도 `property` 선언 목록까지 전부 포함됐는지 확인할 것 — 일부 레시피는 지면상 `_T`/타이머 프로퍼티 선언을 생략하고 있다.
- **`PlayerAttack.DoAttack()`을 `maker_execute_script`로 직접 호출해 전투를 테스트할 때, `PlayerControllerComponent.LookDirectionX`가 이동 입력 없이는 갱신되지 않아 공격이 몬스터 반대 방향으로 나갈 수 있다.** `msw-combat-system` §9-1이 이미 문서화한 케이스("Auto-attack / AI-triggered attack must set facing first")를 실제로 겪음 — 플레이어를 몬스터 옆으로 순간이동시킨 뒤 곧바로 `DoAttack()`을 호출하면 `LookDirectionX`는 마지막 실제 이동 입력 방향(이 세션에선 -1, 왼쪽)에 머물러 있어서 공격 판정 박스가 몬스터 반대편에 생성됐다. **해결**: 스크립트로 직접 공격을 트리거하기 전에 `controller.LookDirectionX = (targetX >= selfX) and 1 or -1`로 명시적으로 향해준다. 실제 키/터치 입력으로 플레이하는 정상 경로는 이동 시 자동 갱신되므로 이 문제와 무관 — 이건 순수히 "이동 없이 직접 스크립트로 공격만 트리거하는" 테스트 방법론의 함정이다.

### Architecture risk — single shared `currentIndex`

`OnDeleteTouched()` (and the world "생성" button) always act on `self._T.currentIndex`, not on "whichever slot the user thinks they picked." Selection is a **separate prior step** (`OnStandeeTouched` updates `currentIndex`) from the destructive action (delete). If a standee click is ever missed/mis-registered, `currentIndex` silently stays on the last *successful* selection, and the next delete removes that slot instead of the one the user was looking at. This was the leading theory behind an earlier user report of "only the last-created character is deletable" — since **confirmed** to have been exactly this: missed clicks caused by the `TouchReceiveComponent` narrow-hitbox bug (see Gotchas + "Resolved report" below), not a bug in the `currentIndex` model itself. Now that click detection is reliable (`ScreenTouchEvent`-based), `currentIndex` reliably tracks the last-touched slot and this risk is latent rather than active — but the design coupling (selection and delete sharing one index) is still worth keeping in mind if a future feature reintroduces missed/async selection (e.g. multi-touch, network lag on a synced index).

### Gotchas (do not redo these mistakes)

- **`TextRendererComponent.FontSize` is not in world units.** It's a separate scale — values in the 2.5–6 range read as normal text at this project's camera zoom; 0.6 is nearly invisible, 40 fills the screen. Tune visually via screenshot, don't guess from `RectSize`.
- **`SortingLayer` must match the map's actual `MapLayerComponent.MapLayerName`**, not a guessed default like `"MapLayer0"`. Check via `MapBuilder.component(mapLayerEntityName, "MOD.Core.MapLayerComponent")` before setting world text/sprite `SortingLayer`.
- **Avatar rendering needs its own child entity, not the root.** `AvatarRendererComponent`+`CostumeManagerComponent` on the same root Transform as a foothold-offset silhouette sprite renders the avatar floating in mid-air (avatar = foot-pivot, silhouette = center-pivot workaround). Put the avatar stack on a child with a local Y offset canceling the root's offset.
- **`TouchReceiveComponent` is unreliable on any entity that swaps its visible renderer between a root `SpriteRendererComponent` and a child `AvatarRendererComponent`** (exactly the standee's empty↔filled swap). Confirmed root cause: an occupied standee's actual touch hitbox is only ~±15px around the exact `TransformComponent` center — far smaller than the visible avatar sprite a human naturally clicks at torso/face height. This held regardless of setting: `AutoFitToSize=true` (baseline), `AutoFitToSize=false` + fixed `TouchArea` up to `(1.2,2.2)`, and even `TouchArea=(4,4)` all failed the same off-center-click test. **Fix applied: removed `TouchReceiveComponent` from the standee model entirely**, replaced with a global `_InputService:ConnectEvent(ScreenTouchEvent, ...)` handler on the stage controller that converts the touch point via `_UILogic:ScreenToWorldPosition()` and does a manual box-distance hit test against each standee's real world position (see Data flow). Filtered by `_InputService:IsPointerOverUI()` so UI-button clicks aren't double-handled. Verified via repeated off-center click regression tests on both empty and occupied slots. **If a future entity needs click detection and also swaps renderers (sprite↔avatar, sprite↔skeleton, etc.), assume `TouchReceiveComponent` will have the same narrow-hitbox problem and go straight to the `ScreenTouchEvent` pattern instead of re-testing `TouchArea` tuning.**
- **UI-attached components cannot call `@ExecSpace("Server")` service methods directly** in this world (`ServiceAuthorityCheck=true` in `WorldConfig.config` → `[LEA-3022] InvalidExecSpace`). Route server calls through a real map/world-entity component instead (see `RequestEnterGame` on `CharacterSelectStageController`, called from the UI card via `GetComponent`).
- **`table` is a valid cross-boundary RPC parameter type** (client→server `@ExecSpace("Server")` calls) — confirmed working for a flat table of 6 strings (`look`). Prefer this over long individual-argument lists when a script boundary is crossed.
- **World UI panels here do not block world-entity touch input by default** (`raycast: false` is the builder default for `panel()`). A standee positioned underneath an open card UI is still clickable — don't assume "the card covers it" explains an input bug.
- **`SpawnLocationComponent`-bearing entities must be named exactly `SpawnLocation`.** Maker auto-suffixes duplicates (`SpawnLocation_1`, `_2`, ...) which the engine rejects (`[LEA-3021]`) — multiple entities sharing the identical name `SpawnLocation` is the correct/expected pattern for this component, not a conflict. Fix via `MapBuilder.rename()`.
- **World start map is a Maker-project-level setting with no corresponding workspace file** (no `Global/SectorConfig.config` in this project). Cannot be set by AI file edit — user must configure it in the Maker UI. Verify via `maker_get_current_map()` after `play`.

This affected `CharacterStandee.model`'s `CreateBg`/`CreateBorder`/root silhouette and `WorldButton.model`'s root fill/`Border` — all originally authored with the wrong (too-small) assumption; corrected 2026-07-16.
  **✅ Generalized and confirmed 2026-08-03 (5th session)**: the "specific to this one placeholder RUID?" question was open until this session. ### Resolved report — "combat power (전투력) is identical across every character after swapping"

User report (2026-08-12): "다른 캐릭터로 전환했을때, 각 캐릭터의 전투력이 캐릭터마다의 스탯별로 달라야하는데, 모두 같은 모습 보임" (swapping to a different character in the Lobby should show a different CP per character's stats, but every character showed the same value). Root-caused and fixed:

- **`PlayerAttack.mlua`'s combat-facing properties (`AttackDamage`/`CriticalChance`/`CritDamageMultiplier`/`AttackCooldownSeconds`/`Accuracy`) were plain `property number`, not `@Sync`.** `PlayerStatsComponent.RecalculateDerived()` (the method that actually writes per-character values into these fields from Str/Dex/Intel/Luk) runs `@ExecSpace("ServerOnly")`. `CharacterInfoUIController.Refresh()` (which computes and displays the CP badge) runs `ClientOnly` and reads these same fields off the client's own copy of `PlayerAttack`. Without `@Sync`, the server's writes never reached the client — the client always read the script's declared defaults (`AttackDamage=50`, `CriticalChance=0.3`, `CritDamageMultiplier=1.5`, `AttackCooldownSeconds=0.6`, `Accuracy=91`) no matter which character was actually active server-side, so the CP formula (which depends only on these fields) always produced the same number. This also explains a suspicious "958, round-number-looking" CP value seen during an earlier, unrelated verification pass in this same session — that was this exact bug, just not recognized as one at the time.
- **Fix**: added `@Sync` to all 5 properties. **Verified via direct reproduction** (`maker_execute_script`, matching this project's established practice): called `_CharacterRosterLogic:SwapActiveCharacter(...)` twice from the client context with two roster characters with very different stats (slot 1: str5/dex6/intel3/luk6 → server computed `attackDamage=17.5, critChance=0.068, critMult=1.53, cooldown=0.583, accuracy=96`; slot 6: str2/dex7/intel2/luk9 → server computed `attackDamage=13.0, critChance=0.077, critMult=1.545, cooldown=0.580, accuracy=97`), then read `_UserService.LocalPlayer:GetComponent("script.PlayerAttack")`'s fields **on the client** after each swap — client values now exactly matched each character's own server-computed values (previously would have stayed frozen at the declared defaults). Resulting CP differed correctly (slot 1 ≈ 311, slot 6 = 233).
- **General lesson**: any property a `ServerOnly` method writes and a `ClientOnly` UI reads must be `@Sync` (or `@TargetUserSync`) — a script component's own `property` fields do **not** sync across server/client by default, only engine-native component fields with their own built-in sync behavior do. When a client-side display looks "stuck" at one value regardless of server-side state changes, check `@Sync` on the read fields before suspecting the write-side logic.

### Resolved report — "some skills let a basic attack chain in right after they're used"

User report (2026-08-12): "몇몇 스킬들은 사용 이후에 기본 공격이 이어서 나갈때가 있는데" (after using some skills, the basic attack sometimes fires right afterward). Root-caused and fixed:

- **`PlayerSkillComponent.UseSkill()` and `PlayerAttack.DoAttack()` were two fully independent cooldown pipelines with no shared lock.** `PlayerControllerComponent:SetActionKey` fires a fresh `PlayerActionEvent` for a held combat-action key on every tick (confirmed by the pre-existing necessity of `DoAttack`'s own `AttackCooldownSeconds` gate against `LastAttackTime` — that gate only makes sense if the Attack action re-fires continuously while Ctrl is held, not once per keypress). A player holding the Attack key (normal muscle-memory for continuous auto-attacking) while tapping the Skill key (Q) would have their independently-ticking `AttackCooldownSeconds` window happen to lapse right as/just after the skill resolved — since every skill kind except dash's physics impulse resolves synchronously within the same server tick (no `wait()` anywhere in `DoMeleeSingle`/`DoRanged`/`DoMultiHit`/`DoBuff`), nothing separated "skill just fired" from "held key's next due tick" in wall-clock time. This is exactly why the report said "일부 스킬" (some skills) and "이어서 나갈때가 있다" (sometimes) rather than every time — it's a coincidental-timing race between two unsynced timers, not a defect in any specific skill's own logic.
- **Fix**: `UseSkill()` now also refreshes `PlayerAttack.LastAttackTime` to `_UtilLogic.ElapsedSeconds` immediately after a successful skill use (same place `LastUseTime`/`CurrentMp` are already updated). This gives skill use authority over the shared attack timer, matching classic MapleStory behavior where using a skill also resets your basic-attack timer.
- **Verified via direct reproduction** (`maker_execute_script` on `server_main`, matching this project's established practice): set `attack.LastAttackTime` far in the past (simulating an already-due held Attack key), called `skillComp:UseSkill()` (dash), then immediately called `attack:DoAttack()` to simulate the held key's very next tick. Before the fix this second call would execute a full attack (the two timers never interacted); after the fix, `attack.LastAttackTime` after `UseSkill()` (93.312) was unchanged by the follow-up `DoAttack()` call — the attack was correctly suppressed. A separate sanity check (`DoAttack()` alone, with no preceding skill use, after the cooldown had genuinely elapsed) confirmed normal auto-attacking still fires unaffected (`fired=true`).
- **General lesson**: whenever two combat actions on the same entity are each gated by their own independent `ElapsedSeconds`-based cooldown timer, check whether they need to share (or push) a timer to prevent one from silently sneaking through during/right after the other — independent per-action cooldowns are correct in isolation but can race when both can be triggered by the same held/repeating input source.

### Full-codebase audit — 3 confirmed system-wide bugs found and fixed (2026-08-12)

User request: "게임 전체적으로 분석해서 시스템 상 오류 있다면 해결해" (analyze the whole game, fix any systemic errors). Read all 24 `.mlua` files under `RootDesk/MyDesk/` in full (every script that hadn't already been reviewed this session), looking for the same bug *classes* already found earlier this session (missing `@Sync`, unlinked cooldown timers, duplicate handlers). Found 3 real, confirmed bugs (each verified via direct `maker_execute_script` reproduction, not just code review) and ruled out several plausible-looking leads that turned out to be correct as-is:

**Fixed:**

1. **Duplicate "I" key handler double-toggled the Inventory window (net no-op most presses) — the actual cause of the "I 키가 가끔 안 먹힌다" mystery from 2026-08-11/2026-08-12, previously misdiagnosed as input-simulator noise.** `LobbyStageController.OnKeyDown` hardcoded `if event.key == KeyboardKey.I then ... controller:Toggle() end`, while `WindowHotkeyLogic` (a global `@Logic`, always active) *also* listens to the same `KeyDownEvent` and toggles the same `/ui/InventoryGroup` window via the rebindable `KeyBindingLogic` registry (`"Inventory"` action, default key also `I`). Both handlers fire on every keypress while in the Lobby, so the window toggled twice per press — open→closed or closed→open→closed, reading as "nothing happened" almost every time. The hardcoded copy also silently ignored any key the player rebound Inventory to via the Key Settings popup, since it never consulted `KeyBindingLogic` at all. **Fix**: removed the hardcoded block from `LobbyStageController.OnKeyDown` entirely, leaving `WindowHotkeyLogic` as the single correct handler (it already exists specifically for this and is rebind-aware). Verified via `maker_keyboard_input`: one "I" tap now reliably opens the window (`Enable` false→true), a second tap reliably closes it (true→false) — both single-toggle, no double-fire. The kept `UpArrow`-at-portal return-to-select logic in the same handler was re-verified working (teleport to `choice_map` fired correctly).
2. **Piercing skills (`arrowblow`/애로우 블로우) could deal 2+ hits worth of damage to the same monster from one cast, instead of the intended one hit per pierced target.** `ProjectileComponent.OnUpdate`'s hit-check *read* `self._T.hitList[monsterEntity.Name]` to skip already-hit monsters, but never *wrote* to it anywhere — so a `Pierce=true` projectile (which doesn't self-destroy on hit, only on `MaxLifetime`) kept re-hitting the same monster on every subsequent tick it remained within `HitRadius`. Confirmed via direct repro: a stationary target took 2 full hits (34 damage instead of 17) from a single non-repeated cast before the fix. **Fix**: `self._T.hitList[monsterEntity.Name] = true` is now set at the moment a hit registers, before calling `OnHit()`. A non-Pierce shot never hit this bug (it destroys itself and returns on its first hit), so `melee_single`/`multi_hit`/`ranged_single` skills were unaffected.
3. **The skill-cooldown countdown shown in the player HUD used two different, unsynchronized clocks and could display a slightly wrong remaining time (or show "READY" a bit early).** `PlayerSkillComponent.UseSkill()` stamps `LastUseTime` server-side (`@ExecSpace("ServerOnly")`) using the server's own `_UtilLogic.ElapsedSeconds`. `PlayerHUDController.Tick()` (client-only) then computed `def.cooldown - (_UtilLogic.ElapsedSeconds - skill.LastUseTime)` using the **client's own** `ElapsedSeconds` — confirmed via direct side-by-side read (`maker_execute_script` on both `client` and `server_main` contexts) that these are genuinely different, unsynced per-process clocks (measured ~0.5s apart in one sample, ~1.4s in another), not the same value exposed twice. **Fix**: swapped to `_UtilLogic.ServerElapsedSeconds`, which is the server's clock as replicated to the client (confirmed distinct from local `ElapsedSeconds` and tracking close to the server's own value, accounting for sync latency) — the correct clock to compare against a server-stamped timestamp. No other `ElapsedSeconds` usage in the codebase has this problem: every other read/write pair either stays consistently server-side (`PlayerAttack.LastAttackTime`, `PlayerSkillComponent.BuffExpireTime`) or consistently client-side (`CharacterSelectStageController`'s double-click timing) — checked all of them during this audit.

**Investigated and ruled out (real leads, confirmed correct as-is — recorded so a future session doesn't re-investigate from scratch):**

- `ProjectileAttackComponent`'s `Damage`/`CriticalChance`/`CritDamageMultiplier` are plain (non-`@Sync`) properties, same shape as the earlier `PlayerAttack` CP bug — but these are only ever read server-side inside the attack-resolution pipeline (`CalcDamage`/`CalcCritical`/`GetCriticalDamageRate`, all part of the server-authoritative hit pipeline), never displayed client-side, so the missing `@Sync` has no observable effect. Not a bug.
- `ProjectileComponent.OnHit()` reads `self.Entity.AttackComponent` via **dot access**, even though the actual attached script is the *user* component `script.ProjectileAttackComponent extends AttackComponent`. Per the documented rule, dot access normally only resolves engine-native components — this looked like exactly the kind of bug that would make every ranged skill silently deal zero damage. **Empirically confirmed NOT a bug**: `extends AttackComponent` (and by extension `HitComponent`) is a special engine "system extension" point, and the dot-access does resolve correctly (`isvalid(proj.AttackComponent) == true`, confirmed live). An initial "ranged skill deals 0 damage" repro during this investigation turned out to be a **test-methodology artifact**, not a real bug: the test monster has a `RigidbodyComponent`, and directly writing `slime.TransformComponent.WorldPosition = ...` on a Rigidbody entity is silently overwritten by physics the next frame (documented in this project's own skill references) — the monster never actually moved to where the projectile was fired, so the projectile correctly missed. Re-tested with a freshly-spawned monster at the intended position instead of repositioning an existing Rigidbody entity, and ranged damage applied correctly end-to-end.
- `AttackComponent:AttackFrom(Vector2 size, Vector2 position, string attackInfo, CollisionGroup group)`'s exact signature was verified against the real engine API (`mlua_api_retriever`) rather than assumed — matches what `ProjectileComponent.OnHit()` already calls. Confirmed correct, not a hallucinated API.
- No other `KeyDownEvent` listener in the codebase overlaps with another the way `LobbyStageController`/`WindowHotkeyLogic` did (grepped all 3 remaining `ConnectEvent(KeyDownEvent, ...)` call sites after the fix — `KeyBindingPopupController` only reacts to `P`, `WindowHotkeyLogic` and the now-trimmed `LobbyStageController` no longer overlap on any key).
